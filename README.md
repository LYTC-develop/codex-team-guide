# 從 ChatGPT 到 Codex：把 AI 用進每天的工作

**[開啟圖文教學網站 →](https://lytc-develop.github.io/codex-team-guide/)**

網站提供手機／電腦版面、章節導覽、可展開的名詞解說，以及可複製的職務任務。以下保留 Markdown 教材，方便在 GitHub 直接閱讀。

給已經使用 ChatGPT，希望用 Codex 完成美編、財務與行政工作的同事。

這份教材教你看懂工作環境、交代任務、取得成果，以及確認工作真的完成。先讀共同概念，再選一個與職務相關的案例。不需要先學寫程式。

> 美編案例依公司既有工作包編寫，該工作包需要組織存取權；財務與行政為練習情境，尚未代表公司已完成系統串接。

## 1. 這次要學會的工作方式

把一件工作連同資料、規則與交付要求交給 Codex，讓它在指定專案中執行，再由你驗收。

例如製作商品銷售圖，你需要給它商品照片、已確認的賣點與價格、品牌規範、交付尺寸；最後要拿到圖片、圖上文案、資料來源與校對紀錄。

ChatGPT 也能處理檔案與使用工具。這次團隊導入的重點，是以 Codex 的專案工作方式，把公司流程、素材與成果管理起來。實際能執行哪些工作，取決於該環境可用的工具與權限。

**共同流程：開啟專案 → 確認資料與工具 → 交代成果 → 執行與修正 → 驗收 → 保存交接。**

## 2. 先認識這些名詞

不用背英文全名，先知道它在工作中負責什麼。

### 工作放在哪裡？

| 名詞 | 工作中怎麼理解 | 你會遇到的例子 |
|---|---|---|
| Project／專案 | 圍繞同一項工作整理資料與任務；本教材主要使用本機專案資料夾 | 商品銷售圖、每月對帳各用自己的專案 |
| Git | 記錄檔案版本變更的工具 | 知道工作包改了什麼、必要時找回舊版 |
| GitHub | 託管 Git 專案並協作的平台 | 公司在上面提供工作包、教學與更新 |
| Repository／Repo／儲存庫 | 一套由 Git 管理的檔案與版本紀錄 | 商品一頁式工作包就是一個 Repo |
| Clone／Pull | Clone 是首次取得本機儲存庫；Pull 是把遠端更新整合進來 | 第一次 Clone，以後依專案規則更新 |
| Commit／Push | Commit 是在本機記錄一批變更；Push 是把提交送到遠端 | 存檔不等於已提交，提交也不等於已上傳 |
| README／Markdown | README 是入口說明；Markdown 是用簡單標記寫標題、表格與連結的文字格式 | 你現在閱讀的就是 README.md |

下載 ZIP 可以取得檔案，但沒有完整的 Git 工作流程，不能直接當成 Clone 後的專案來 Pull。GitHub 也不會自動備份電腦裡所有素材與產出。

### Codex 怎麼照公司方法做事？

| 名詞 | 工作中怎麼理解 | 你會遇到的例子 |
|---|---|---|
| Agent／代理 | 能依任務安排步驟、使用工具並檢查結果的 AI 系統 | 讀商品資料、查來源、做分鏡，再製圖與檢查 |
| Context／上下文 | AI 這次工作取得的資料、對話與規則 | 商品規格、品牌偏好、上一版修改原因 |
| AGENTS.md | 給 Codex 讀取的專案工作指引；它不是技術性的權限鎖 | 規定素材位置、製作流程與交付方式 |
| Skill／技能 | 可重複使用的工作指引，可附範本、參考資料與程式 | 商品銷售分鏡、圖片校對流程 |
| Tool／工具 | AI 實際執行操作的能力 | 讀檔、查網頁、生圖、操作試算表 |

**Skill 規範怎麼做；Tool 提供實際操作能力。** 裝了製圖 Skill，仍要有可用的圖片工具。開了新任務，也別假設它已讀過其他任務裡的資料。[官方 Skill 說明](https://learn.chatgpt.com/docs/build-skills)

### Codex 怎麼連到外部系統？

| 名詞 | 工作中怎麼理解 | 你會遇到的例子 |
|---|---|---|
| API | 系統提供給程式讀取資料或執行操作的介面 | 訂單系統提供查詢訂單的 API |
| MCP | 讓 AI 用共同規格連接工具與資料的協定 | Codex 透過支援的 MCP 服務取得查表、讀文件等能力 |
| Plugin／外掛 | 可安裝的擴充套件，可包含 Skills、工具連接等內容 | 安裝與工作相關的能力套件 |
| OAuth／API Key | OAuth 常見為登入後授權存取；API Key 是服務辨識呼叫者的憑證之一 | 連到指定帳號，取得被允許的讀取或修改能力 |

例如，某個整合**可以**這樣運作：

```text
你交代「整理本月未對上的款項」
  → Codex 選擇查帳工具
  → MCP 服務接收工具要求
  → 服務透過系統 API 取得資料
  → Codex 比對資料並製作差異清單
```

這是常見的串接方式之一。MCP 也能連本機工具，不一定經過外部 API；Codex 也可能直接執行程式呼叫 API。連接成功後能做什麼，還要看工具提供哪些操作及帳號權限。[官方 MCP 說明](https://learn.chatgpt.com/docs/extend/mcp)

首次使用時可以先說：「請確認這個專案目前可用的工具、可讀取的資料，以及完成本任務還缺少什麼。」不需要為了入門，先自己建 API 或 MCP。

## 3. 美編案例：製作一組商品一頁式銷售圖

**工作價值：** 把商品資料轉成可交給網站人員上架的圖組，保留依據與修改紀錄，減少來回交接。

使用公司既有的 [商品一頁式工作包](https://github.com/LYTC-develop/product-landingpage-starter)。有存取權的同事依該專案 README 首次 Clone，並用 Codex 開啟包含 README.md 與 AGENTS.md 的根目錄。

| 你準備 | Codex 執行 | 交付與驗收 |
|---|---|---|
| 商品照片、規格、賣點依據、售價、品牌規範、客群 | 市場研究、銷售分鏡、逐張製作、手機預覽與校對 | 按順序命名的圖組、文案、來源、交付清單；你確認產品、價格、文字與手機可讀性 |

可直接改用的任務：

> 請先讀取 AGENTS.md，使用 yf-mobile-sales-page，依 personal/ 本次商品的資料製作八張手機一頁式銷售圖。先查相關市場案例，整理每張圖的購買理由、文案與證據，再依分鏡完成圖組。缺少依據的數字或賣點列為待確認。交付放 outputs/ 本次活動資料夾，包含依序上傳的圖片、文案逐字稿、來源與手機檢查結果。我要能交給網站同事上架的檔案。

先確認你的 Codex 環境有可用的生圖工具與額度。需要可編輯文字層時要明說；PNG／JPG 本身是平面圖。

公司工作包的 [蕎麥麵首圖範例](https://github.com/LYTC-develop/product-landingpage-starter/tree/main/examples/buckwheat-hero) 可用來理解「商品利益 → 數字來源 → 視覺呈現 → 校對」；目前該範例是單張首圖，不是已完成的八張圖組。正式商品數字要核對本次資料。

**你在這裡會用到：** GitHub／Clone 取得工作包、AGENTS.md 理解規則、Skill 重用製作流程、Tool 執行製圖。依現有工作包規則，personal/ 與 outputs/ 不進 Git，需另依公司方式保存與交接。

## 4. 財務案例：訂單與收款對帳

**工作價值：** 讓財務優先處理差異與例外，並能逐筆回查原因。

先用匯出的訂單與收款檔練習；需要直接讀系統時，再接 API 或 MCP 工具。本教材未附真實帳務資料，也未預設已接通公司系統。

| 你準備 | Codex 執行 | 交付與驗收 |
|---|---|---|
| 同期間訂單、收款、退款、手續費資料，以及配對與入帳日規則 | 統一欄位、依規則配對、計算差額、列出例外 | 對帳表、未配對清單、總額核對與來源列號；你檢查差異及重要款項 |

> 請先盤點我提供的本月訂單、收款與退款資料，說明可使用的配對欄位。依我提供的對帳規則處理，將退款、手續費與跨期入帳分開列示。輸出對帳工作簿，包含已配對、未配對、差額及來源檔名與列號，並核對輸入與輸出筆數、金額。缺少規則或配對不唯一時，列出待確認項目。本次交付對帳報表，不變更正式帳務。

**完成標準：** 每筆例外找得到來源；筆數與金額能勾稽；不能只用一段「本月大致正常」作為交付。這個練習不需要先學會串接系統。

## 5. 行政案例：建立合約到期與待辦清單

**工作價值：** 把散落的合約整理成可追蹤、可交接的清單。

| 你準備 | Codex 執行 | 交付與驗收 |
|---|---|---|
| 合約檔、公司負責人對照表、整理基準日 | 擷取對象、期限、續約與通知條款，計算待辦日期 | 到期表、缺件表、待確認事項；每項日期附原文與來源位置 |

> 請整理我提供的供應商合約，建立合約台帳與未來 90 天待辦清單。擷取合約對象、生效日、到期日、自動續約、提前通知條件與內部負責人。計算出的日期請附計算依據；每筆資料附來源檔名與頁碼。條款不清楚、掃描辨識不確定或缺少負責人的項目列為待確認。交付可編輯表格，本次不寄信或通知外部對象。

**完成標準：** 關鍵日期能回查原文；缺資料不補猜；有負責人與後續動作。若日後要寫入 Google Sheets 或行事曆，再確認對應工具及寫入權限。

## 6. 每次交代任務，說清楚這五件事

| 要交代的事 | 例子 |
|---|---|
| 目標 | 做出能交給網站同事上架的一組銷售圖 |
| 資料位置 | 本次商品資料放在 personal/ 指定活動資料夾 |
| 規則 | 商品數字依本品資料，依公司工作包流程製作 |
| 交付物 | 圖片、逐字文案、來源、校對紀錄 |
| 完成標準 | 手機看得清楚、規格正確、資訊可核對、檔案可開啟 |

遇到問題時，把實際錯誤與預期結果交給 Codex。例如：「你交付的表格少了三筆退款，請依原始收款檔重新核對筆數與總額，修正報表並說明差異。」

交付時確認三件事：**成果在哪裡、驗證過什麼、還有哪些待確認。**「已規劃」「已生成」「已儲存」「已上架」是不同狀態。

## 7. 教材與日常工作分開保存

GitHub 教材放操作說明、空白範本與可公開的示例；實際客戶、合約、帳務與憑證留在公司指定位置。連線憑證透過工具提供的登入或憑證設定流程處理。

學完後，你應能拿自己職務的一項工作，找到專案與資料、確認工具、交代交付標準，並驗收實際成果。
