01 從 ChatGPT 到 Codex

你已經會與 AI 對話。
現在，讓它一起完成工作。

把資料、工具與公司流程放進同一個專案。
從商品銷售圖到對帳報表，學會交代任務，也學會驗收成果。

適合已使用 ChatGPT 的同事不需先學寫程式
讀完你會知道資料放哪裡
工具如何協作AI 怎麼動手做
成果如何判斷什麼才算完成
↳

這次的重點，是建立能重複使用的工作流程。ChatGPT 也能使用工具與處理檔案；團隊選擇用 Codex，把專案資料、製作方法與成果管理起來。

02 先建立共同語言

名詞不用背，先知道用途。

先讀一句話解釋。
展開卡片，看工作中的例子。

A 工作放在哪裡？

Project 專案同一項工作的資料與任務集合。
本教材主要使用本機專案資料夾。美編銷售圖、每月對帳各有自己的資料與流程；開始前先確認開啟的是哪一個專案。
Git / GitHubGit 記錄版本；GitHub 提供線上協作。
Git 能記錄檔案改了什麼。GitHub 託管 Git 專案，讓公司分發工作包與更新。存在電腦上的檔案，不會因此自動上傳。
Repository 儲存庫 / Repo一套由 Git 管理的檔案與版本紀錄。
例如公司「商品一頁式工作包」就是一個 Repo，裡面有教學、規範、範本與技能。Repo 可以公開，也可以只讓有權限的人存取。
Clone / Pull首次取得專案；之後整合遠端更新。
第一次用 Clone 取得本機儲存庫，以後按專案規則 Pull 更新。下載 ZIP 只取得一份檔案，不能直接當成 Clone 後的專案來 Pull。
Commit / Push在本機記錄變更；再送到遠端。
存檔、Commit、Push 是三個步驟。Commit 是記錄一批變更，Push 才把提交送到 GitHub。被 .gitignore 忽略的工作資料，不會隨一般提交上傳。
README / Markdown專案入口說明，以及容易閱讀的文字格式。
第一次取得工作包，先讀 README.md。Markdown 用簡單標記寫標題、清單、表格與連結；.md 就是常見副檔名，不需要寫網頁程式才能修改內容。

B AI 怎麼照公司方法做事？

Agent 代理能安排步驟、使用工具並檢查結果的 AI 系統。
你交代要做商品圖，Agent 可以讀資料、查來源、編分鏡、呼叫圖片工具，再檢查產出。能做哪些事，取決於現有工具與權限。
Context 上下文AI 這次工作取得的資料、對話與規則。
商品規格、品牌偏好、上一版修改原因都是上下文。開新任務時，提供檔案位置與必要背景；別假設它已讀過其他任務裡的資料。
AGENTS.md給 Codex 讀取的專案工作指引。
例如規定素材放哪裡、先做哪些研究、最後交付什麼。它協助 AI 遵循團隊流程，但不是技術上的權限鎖。
Skill 技能一套可重複使用的工作指引。
Skill 可以附範本、參考資料與程式，例如銷售分鏡或圖片校對流程。它教 AI 怎麼做；要實際生圖，還需要可用的圖片工具。
Tool 工具AI 真正執行操作的能力。
讀檔、查網頁、生圖、操作試算表都是工具能力。當 AI 說無法存取或操作時，先檢查工具與授權，單純改提示詞未必能解決。

C 怎麼連到公司的其他系統？

API系統給程式讀資料、執行操作的介面。
例如訂單 API 讓程式查詢訂單，而不必人工下載報表。不同 API 提供的操作不同，可能有權限、額度或收費限制。
MCP讓 AI 用共同規格連接工具與資料的協定。
全名是 Model Context Protocol。MCP 服務可以提供查表、讀文件等工具；工具背後可能呼叫 API，也可能操作本機檔案。接上 MCP 不代表取得所有系統能力。
Plugin 外掛可安裝的擴充套件。
外掛可打包 Skills、工具連接等內容，讓團隊更容易安裝工作能力。安裝完成後，仍要確認需要的帳號授權與工具是否可用。
OAuth / API Key讓系統辨識身分、授予存取能力的方式。
OAuth 常見為登入帳號後同意授權；API Key 是服務辨識呼叫者的憑證之一。讀取、修改可能是不同權限。使用工具的登入或憑證設定流程，不把金鑰放進教材或任務內容。

能力說明：OpenAI Skills ↗OpenAI MCP ↗

03 把名詞連成工作流程

從一個需求，到一份成果。

以訂單對帳為例

「幫我找出本月還沒對上的款項。」

  1. 01Codex

    讀取規則
    安排比對步驟

  2. 02MCP 工具

    提供查帳操作
    傳遞資料要求

  3. 03系統 API

    查詢授權範圍內
    的訂單與收款

  4. 04對帳報表

    列出差異與來源
    交由你驗收

Skill沿途套用公司方法：怎麼配對、怎麼處理例外、怎麼檢查總額。

這是一種串接方式，並非每項任務都需要 MCP 或 API。手邊已有 Excel／CSV 檔，就可以先從檔案開始；需要持續讀取系統資料時，再處理串接。

先確認能力，再交付工作。

可以直接問 Codex：「請確認這個專案目前可用的工具、可讀取的資料，以及完成本任務還缺少什麼。」

01 / 美編與行銷

做出一組能交接的
商品銷售圖。

公司既有工作包

從商品資料出發，完成研究、銷售分鏡與圖組，讓網站同事拿到檔案就知道怎麼上架。

你準備

商品照片、規格、賣點依據、售價、客群與品牌規範。

Codex 執行

市場研究、逐張分鏡、製圖、手機預覽與文字校對。

你驗收

產品與價格正確、手機看得清楚、檔案排序與尺寸符合上架需求。

應拿到的成果

銷售圖組 ＋ 文案逐字稿 ＋ 資料來源 ＋ 校對與交付清單

可以這樣交代任務

請先讀取 AGENTS.md，使用 yf-mobile-sales-page，依 personal/ 本次商品的資料製作八張手機一頁式銷售圖。先查相關市場案例，整理每張圖的購買理由、文案與證據，再依分鏡完成圖組。缺少依據的數字或賣點列為待確認。交付放 outputs/ 本次活動資料夾，包含依序上傳的圖片、文案逐字稿、來源與手機檢查結果。我要能交給網站同事上架的檔案。

開始前，先確認工作包與素材

這段任務適用公司 商品一頁式工作包 ↗。該儲存庫需要存取權；先依 README Clone，再用 Codex 開啟專案根目錄。

確認圖片工具與額度可用。需要可編輯文字層時要明說，PNG／JPG 本身是平面圖。既有蕎麥麵範例是單張首圖，完整圖組仍需依本次商品製作；數字也應核對本批次標示。

這個工作包的 personal/ 與 outputs/ 不進 Git，要另外保存與交接；其他專案依各自規則處理。

這裡會用到GitHubCloneAGENTS.mdSkillTool
02 / 財務對帳

讓每筆收款差異，
都有來源可查。

檔案練習情境

先用匯出的報表完成比對，讓財務把時間放在差異與例外處理。這個案例不預設已串接公司系統。

你準備

同期間的訂單、收款、退款、手續費資料，以及配對與入帳日規則。

Codex 執行

統一欄位、依規則配對、計算差額、標記跨期與未配對款項。

你驗收

總額與筆數能核對；例外能回查來源；配對不唯一的項目有標記。

應拿到的成果

對帳工作簿 ＋ 未配對清單 ＋ 差異原因 ＋ 來源檔案與列號

可以這樣交代任務

請先盤點我提供的本月訂單、收款與退款資料，說明可使用的配對欄位。依我提供的對帳規則處理，將退款、手續費與跨期入帳分開列示。輸出對帳工作簿，包含已配對、未配對、差額及來源檔名與列號，並核對輸入與輸出筆數、金額。缺少規則或配對不唯一時，列出待確認項目。本次交付對帳報表，不變更正式帳務。

什麼時候才需要 API 或 MCP？

已有完整匯出檔，就可以先做對帳。若每月都需要手動下載同樣的資料，再評估直接從系統讀取。

串接前確認工具能讀到需要的欄位、帳號與期間。連線成功，只代表取得工具；仍要核對資料完整性與報表計算。

這裡會用到ContextToolAPI / MCP（串接時）
03 / 行政管理

把散落的合約，
變成可追蹤的待辦。

檔案練習情境

建立合約台帳與未來 90 天的待辦，保留日期依據，讓接手的同事找得到原文。

你準備

合約檔、內部負責人對照表，以及整理的基準日期。

Codex 執行

擷取合約期限、續約與通知條件，計算待辦日期，列出缺件。

你驗收

關鍵日期與原文一致；計算依據清楚；未明確的條款保留待確認。

應拿到的成果

合約台帳 ＋ 90 天待辦 ＋ 缺件清單 ＋ 原文頁碼與依據

可以這樣交代任務

請整理我提供的供應商合約，建立合約台帳與未來 90 天待辦清單。擷取合約對象、生效日、到期日、自動續約、提前通知條件與內部負責人。計算出的日期請附計算依據；每筆資料附來源檔名與頁碼。條款不清楚、掃描辨識不確定或缺少負責人的項目列為待確認。交付可編輯表格，本次不寄信或通知外部對象。

從整理文件，到後續協作

先把台帳做準，再決定要不要寫入共享試算表或行事曆。實際更新前，確認帳號、目標檔案、寫入權限與要新增的內容。

日期有疑義時回查原文；需要判斷條款意義的部分，交由負責人確認，不用猜測補滿表格。

這裡會用到ProjectContextToolOAuth（串接時）
05 把方法帶回日常工作

開始前，說清楚這五件事。

  1. 01

    目標

    這份成果要給誰使用、解決什麼問題？

    交給網站同事上架的商品銷售圖。
  2. 02

    資料位置

    哪些檔案是這次工作應採用的來源？

    本次活動資料夾裡的商品照片與規格。
  3. 03

    工作規則

    依照哪一套流程，有哪些必要限制？

    依公司工作包製作，數字以本品資料為準。
  4. 04

    交付物

    最後需要哪些實際檔案？

    八張圖片、文案逐字稿、來源與校對紀錄。
  5. 05

    完成標準

    你會如何檢查這項工作？

    手機可讀、價格正確、尺寸符合、檔案可開啟。
第一次使用，照這個順序。

開啟公司指定的專案 → 讀 README、準備資料 → 請 Codex 確認工具 → 複製並修改職務案例 → 查看產出 → 指出差異，繼續修正。

結果不對，下一句怎麼說？

指出具體差異和要回查的資料，例如：

「你交付的表格少了三筆退款，請依原始收款檔重新核對筆數與總額，修正報表並說明差異。」

如果是無法讀檔、沒有工具或授權過期，先處理環境。讓 Codex 說明已完成的部分與實際卡點。

06 最後一哩路

看到成果，才算完成。

1.

成果在哪裡？

拿到可開啟的檔案或可存取的連結，知道儲存位置與版本。

2.

驗證過什麼？

圖片實際看過、數字核對過、資料能回查；了解檢查範圍。

3.

還差哪些事？

待確認資料、缺件、人工判斷與下一位負責人的工作都要寫清楚。

已規劃 ≠ 已生成 ≠ 已儲存 ≠ 已上架

問清楚現在完成到哪一步，也把下一步交接出去。

共用教材放操作說明、空白範本與可公開的例子。客戶、合約、帳務與實際工作素材，依公司規定保存；不要把它們加入公開教材。
